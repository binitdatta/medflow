Part 1

Technical Example: Enterprise Order Cancellation

LangGraph as an executable state machine for a controlled business process.

Core idea

LangGraph is not limited to conversational agents. It can orchestrate deterministic Python code, REST APIs, policy checks, databases, human approvals, retries and LLM reasoning inside one explicit execution graph.

Business scenario

A user submits the following request:

“Cancel order 1001 because the customer entered the wrong address.”

The application must:

  1. Authenticate and authorize the user.
  2. Load the order from a database or REST API.
  3. Check tenant boundaries and cancellation policy.
  4. Request approval for high-value orders.
  1. Call the downstream Order API.
  2. Retry transient failures.
  3. Record an audit trail.
  4. Return a final business result.

1. Define the shared graph state

Every node receives the current state and returns a partial state update. LangGraph merges that update into the workflow state. 

from typing import Literal, TypedDict

class CancellationState(TypedDict, total=False):
    # Request context
    order_id: str
    tenant_id: str
    user_id: str
    user_roles: list[str]
    cancellation_reason: str

    # Data loaded during execution
    order: dict

    # Authorization and policy results
    authorized: bool
    policy_allowed: bool
    requires_human_review: bool
    human_decision: Literal[
        "APPROVED",
        "REJECTED",
        "PENDING"
    ]

    # Execution status
    cancellation_completed: bool
    retry_count: int
    max_retries: int
    error_type: str | None
    error_message: str | None

    # Final output and audit history
    result: str
    audit_log: list[str]
Technical contract: a LangGraph node usually behaves like State -> Partial State.

2. Implement nodes as ordinary Python functions

A node can call a database, REST API, Keycloak, a policy service, RabbitMQ, an LLM, a vector database or another internal service. 

def authorize_user(state: CancellationState) -> dict:
    roles = state.get("user_roles", [])

    authorized = (
        "order_cancel" in roles
        or "order_admin" in roles
    )

    return {
        "authorized": authorized
    }


def load_order(state: CancellationState) -> dict:
    order = ORDERS_DB.get(state["order_id"])

    return {
        "order": order
    }


def check_cancellation_policy(
    state: CancellationState
) -> dict:

    order = state["order"]

    tenant_matches = (
        order["tenant_id"] == state["tenant_id"]
    )

    status_allowed = order["status"] in {
        "CREATED",
        "PAID",
        "FULFILLING"
    }

    policy_allowed = (
        tenant_matches and status_allowed
    )

    requires_human_review = (
        policy_allowed
        and order["amount"] >= 5000
    )

    return {
        "policy_allowed": policy_allowed,
        "requires_human_review": requires_human_review
    }
LangGraph does not replace the Python functions. It schedules and connects them according to the graph definition.

3. Route execution with conditional edges

Routing functions inspect the updated state and return the name of the next node. 

def route_after_policy(
    state: CancellationState
) -> Literal[
    "human_review",
    "cancel_order",
    "policy_denied"
]:

    if not state["policy_allowed"]:
        return "policy_denied"

    if state["requires_human_review"]:
        return "human_review"

    return "cancel_order"

The workflow topology is declared explicitly instead of being hidden inside an LLM prompt.

4. Implement a real graph cycle for retries 

def route_after_cancellation(
    state: CancellationState
) -> Literal[
    "success",
    "cancel_order",
    "retry_exhausted"
]:

    if state["cancellation_completed"]:
        return "success"

    retry_count = state.get("retry_count", 0)
    max_retries = state.get("max_retries", 3)

    if (
        state.get("error_type")
        == "TRANSIENT_API_ERROR"
        and retry_count < max_retries
    ):
        return "cancel_order"

    return "retry_exhausted"

5. Build and compile the graph 

from langgraph.graph import END, START, StateGraph
from langgraph.checkpoint.memory import MemorySaver

builder = StateGraph(CancellationState)

builder.add_node("authorize_user", authorize_user)
builder.add_node(
    "reject_unauthorized",
    reject_unauthorized_request
)
builder.add_node("load_order", load_order)
builder.add_node("order_not_found", order_not_found)
builder.add_node(
    "check_policy",
    check_cancellation_policy
)
builder.add_node("policy_denied", policy_denied)
builder.add_node("human_review", human_review)
builder.add_node("human_rejection", human_rejection)
builder.add_node("cancel_order", cancel_order)
builder.add_node("retry_exhausted", retry_exhausted)
builder.add_node("success", create_success_response)

builder.add_edge(START, "authorize_user")

builder.add_conditional_edges(
    "authorize_user",
    route_after_authorization
)

builder.add_conditional_edges(
    "load_order",
    route_after_order_lookup
)

builder.add_conditional_edges(
    "check_policy",
    route_after_policy
)

builder.add_conditional_edges(
    "human_review",
    route_after_human_review
)

builder.add_conditional_edges(
    "cancel_order",
    route_after_cancellation
)

builder.add_edge("reject_unauthorized", END)
builder.add_edge("order_not_found", END)
builder.add_edge("policy_denied", END)
builder.add_edge("human_rejection", END)
builder.add_edge("retry_exhausted", END)
builder.add_edge("success", END)

checkpointer = MemorySaver()

graph = builder.compile(
    checkpointer=checkpointer
)

initial_state: CancellationState = {
    "order_id": "1001",

    "configurable": {
        "thread_id": "cancel-order-1001"

}

final_state = graph.invoke(
    initial_state,
    config=config
)
Checkpointing: the thread_id identifies one workflow execution. A persistent production checkpointer can allow long-running workflows to resume after restarts, failures or human-review pauses.

Enterprise design principle

Use the LLM for interpretation, extraction and reasoning. Use graph nodes and enterprise services for authorization, policy enforcement, execution, recovery and auditability.

When LangGraph adds value

Good fit

  • Multiple branches and decision points
  • Cycles and retry behavior
  • Long-running execution
  • Human-in-the-loop approval
  • Checkpoint recovery
  • Multiple tools or agents
  • Workflow visualization and state inspection

Possibly unnecessary

  • One prompt followed by one response
  • A simple synchronous three-step function
  • No branching, persistence or retries
  • No need for workflow observability
  • No need for human interruption or resumption
Part 2

LangGraph as a GPS-Controlled Execution Map

A graph-theory interpretation of nodes, edges, state, routing and cycles.

Your GPS analogy is accurate

LangGraph defines the permitted locations and routes of a workflow. Runtime state determines which permitted route is selected next.

Precise technical definition

LangGraph is a stateful workflow and agent-orchestration library that uses directed-graph concepts to connect executable Python processing nodes through fixed and conditional transitions.

It uses graph theory as an execution model, but it is not primarily a general-purpose graph-analysis library such as NetworkX.

GPS-to-LangGraph mapping

GPS concept LangGraph concept Technical meaning
Current location Current node The processing function currently executing
Destination Workflow objective or END The successful or terminal workflow state
Road Edge A permitted transition between nodes
Intersection decision Conditional edge A router selects the next node using state
Vehicle and trip data Graph state Shared data carried across the execution
Road closure Tool or API failure An execution condition requiring another route
Recalculate route Retry or alternate branch The graph loops or chooses another node
Planned stop Human interrupt Execution pauses until an approval or input arrives
Saved journey Checkpoint Persisted workflow state for recovery or resumption

Nodes are processing points

Nodes are usually ordinary Python functions. LangGraph registers and invokes those functions according to the graph definition. 

def load_order(state):
    order = order_api.get_order(
        state["order_id"]
    )

    return {
        "order": order
    }

builder.add_node(
    "load_order",
    load_order
)

The function remains ordinary Python. Registering it as a node makes it part of LangGraph’s controlled execution topology.

Edges are routing instructions

An edge is not another processing function. It declares where execution is allowed to go after a node completes. 

builder.add_edge(
    "load_order",
    "check_policy"
)
Node A
  |
  |  edge: routing instruction
  v
Node B
The receiving point is the next node. The edge is the connection that directs execution to it.

State is what travels through the route

Conditional edges behave like GPS route selection

A fixed edge always uses the same route:

builder.add_edge(
    "load_order",
    "check_policy"
)

A conditional edge examines the current state: 

def select_next_node(state):
    if state["policy_allowed"]:
        return "cancel_order"

    return "reject_request"


builder.add_conditional_edges(
    "check_policy",
    select_next_node
)

LangGraph ReAct loop

In a ReAct-style graph, the model reasons inside the agent node. If it emits tool calls, execution moves to the tools node. Tool results are added to state, and execution returns to the agent node.

START
agent node
LLM reasons and decides
tool calls?
Yes
tools node
invoke Python functions
↺ return tool results to agent
No
END

graph = StateGraph(AgentState)

graph.add_node(
    "agent",
    agent_node
)

graph.add_node(
    "tools",
    tools_node
)

graph.set_entry_point(
    "agent"
)

graph.add_conditional_edges(
    "agent",
    should_continue,
    {
        "tools": "tools",
        "end": END
    }
)

graph.add_edge(
    "tools",
    "agent"
)

return graph.compile()
Why this is agentic

The model may answer immediately, invoke one tool, or invoke multiple tools across repeated agent → tools → agent iterations. The graph supplies a bounded and inspectable control loop.

Why the map matters in enterprise AI 

LLM request:
"Cancel order 1001"

Graph-enforced route:
authenticate
    → authorize
    → validate tenant
    → check policy
    → request approval
    → cancel order
    → write audit record
    → END

The developer defines the legitimate destinations and transitions. The runtime state selects among those legitimate paths.

Most important takeaway: the LLM can help decide what the user means, but the graph and enterprise services control what actions are allowed and how they must be executed.

Technical summary 

LangGraph =
    typed shared state
    + ordinary Python functions as nodes
    + fixed and conditional edges
    + cycles and retries
    + checkpoint persistence
    + human intervention
    + LLM reasoning where appropriate

In practical terms, LangGraph is the executable route map for a stateful business or agentic workflow.
