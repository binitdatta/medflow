Architecture Walkthrough

How a chat message turns into a database read or write.

Request path
Browser (Bootstrap 5 chat widget)
  -> POST /api/chat/sessions/{id}/messages   (Flask, role read from session)
     -> agent.graph.run_agent(user_query, staff_id, role, hospital_scope)
        -> sets identity contextvars (agent/context.py)
        -> LangGraph role subgraph (Nurse | Pharmacist | Admissions)
           -> ChatAnthropic decides: answer directly, or call a tool
           -> tool call -> agent/api_client.py -> HTTP request to
              this SAME Flask app's own REST endpoint
              (X-Service-Secret + X-Acting-Staff-Id / X-Acting-Role headers)
           -> Flask endpoint (api/*.py) re-checks the role via @require_role
              -> SQLAlchemy model -> MySQL 8
              -> writes an audit_log row if PHI was touched
           -> tool result flows back into the LangGraph loop
        -> final AI message returned as the chat response
Why the agent calls its own REST API instead of the database directly
  • The Flask endpoint is the single place role checks, audit logging, and PHI-shaping logic live — the agent doesn't need to duplicate any of that.
  • A human-built Bootstrap UI and the LangGraph agent hit the exact same contract, so there's only one API surface to secure and test, not two.
  • It's also what makes keycloak/test_confidential_client.sh meaningful: the same endpoints the agent calls can be exercised directly with a Bearer token to prove RBAC holds regardless of caller.
