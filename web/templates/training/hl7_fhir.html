HL7 / FHIR Resource Mapping

Teaching the shape of healthcare interoperability without standing up a full HL7 v2 interface engine.

Why FHIR-shaped, not raw HL7 v2 MLLP

Real hospital integration engines exchange pipe-delimited HL7 v2 messages (ADT, ORM, ORU) over MLLP sockets — valuable to know exists, but not the most productive thing for an intern to build from scratch. This POC instead shapes its REST payloads to mirror FHIR R4 resources, which is where the industry has been moving anyway and maps cleanly onto normal JSON/REST skills.

Example: an ADT-style admit, expressed as REST + JSON

Instead of an HL7 v2 ADT^A01 message, the Admissions subgraph's create_encounter tool posts:

POST /api/encounters
{
  "patient_id": 1,
  "hospital_id": 1,
  "encounter_type": "INPATIENT",
  "chief_complaint": "Shortness of breath"
}

Same real-world event (a patient admission), same downstream effect (a new active Encounter record), expressed as a REST call instead of a segment-delimited message over MLLP. Phase 2 can add a genuine HL7 v2 listener that translates inbound ADT messages into calls against this same endpoint, if that's a skill you want interns to see end-to-end.
