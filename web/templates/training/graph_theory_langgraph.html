Graph Theory, and Why LangGraph Is Named That

LangGraph isn't a marketing name — it's a literal implementation of graph theory concepts that are decades old and show up everywhere from GPS navigation to org charts. This page covers the basic tenets with everyday examples, then maps each one directly onto the LangGraph code already running in MedFlow.

Part 1 — Basic Tenets of Graph Theory

A graph is just two things: a set of nodes (things) and a set of edges (connections between things). Everything below is a variation on that one idea.

Nodes & Edges

The two building blocks of any graph. A node is a thing; an edge is a connection between two things.

Example: Cities are nodes, roads between them are edges. LinkedIn profiles are nodes, connections are edges.

Directed vs. Undirected

An undirected edge goes both ways equally. A directed edge has a specific direction — A connects to B doesn't mean B connects to A.

Example: Facebook friendship is undirected (mutual by definition). Twitter/X following is directed — you can follow someone who doesn't follow you back. A one-way street is directed.

Cycles

A cycle exists when you can follow edges in one direction and eventually return to where you started. A graph with no cycles at all is called a DAG (Directed Acyclic Graph).

Example: A roundabout has a cycle. A family tree does not (you can never be your own ancestor) — that's a DAG. Course prerequisites at a university are also a DAG: nothing can require itself, even indirectly.

Trees

A special case of a DAG: every node has exactly one path back to a single root, and there's exactly one way to reach any node — no shortcuts, no alternate routes.

Example: A company org chart. A computer's file system (every folder has exactly one parent folder). A single-elimination sports tournament bracket.

Weighted Graphs

Edges can carry a number — a cost, distance, or time — not just a yes/no connection. This is what turns "are these connected" into "what's the best way to connect them."

Example: Road distances between cities. Flight prices between airports. Google Maps' "fastest route" is a weighted-graph shortest-path calculation running in real time.

State Machines

A graph where nodes are states a system can be in, and edges are the allowed transitions between them — you can't jump to just any state from any other.

Example: A traffic light: Red → Green → Yellow → Red, and nothing skips straight from Red to Yellow. An elevator door: Closed → Opening → Open → Closing → Closed.

Part 2 — Where Each Concept Shows Up in LangGraph

LangGraph is a directed graph library built specifically for one thing plain graph libraries don't optimize for: cycles with state — an agent that can loop back and try again, carrying what it learned forward each time. Click through each mapping below.

In `agent/graph.py`, every node is just a Python function that takes the current state and returns an update to it. MedFlow's every role subgraph has exactly two nodes:

graph.add_node("agent", agent_node)
graph.add_node("tools", tools_node)

Same concept as a city on a map, just abstracted: a node is "a place execution can be," not a physical location. `agent_node` is where the LLM decides what to do; `tools_node` is where a tool call actually runs.

Every edge in LangGraph is directed, same as a Twitter follow. MedFlow's graph has:

graph.add_edge("tools", "agent")

This means "after tools runs, go to agent" — it says nothing about the reverse direction. The agent → tools direction isn't a plain edge at all; it's conditional (see below), because whether that edge is followed depends on what the LLM decided.

Plain LangChain "chains" are essentially a DAG — data flows one direction through a fixed sequence of steps, no loops allowed. That's fine for "summarize this document," but useless for "keep checking labs and ordering more until you have enough to diagnose."

LangGraph's entire value proposition is supporting real cycles. MedFlow's agent ↔ tools loop can run many times in a single turn:

agent  --tool call requested-->  tools
  ^                                    |
  |____________________________________|

This is a graph with a cycle, on purpose — the Physician subgraph's "check the chart, then order a CT only if needed" behavior from Phase 2 testing is only possible because the graph can go agent → tools → agent → tools as many times as the LLM decides it needs to.

A weighted graph's edge carries a fixed number decided ahead of time (a road's distance never changes mid-trip). LangGraph's conditional edges are the dynamic version of that idea: instead of a fixed weight, each edge has a function that's evaluated fresh every time, using the current state, to decide which path to take:

def should_continue(state):
    last = state["messages"][-1]
    if isinstance(last, AIMessage) and getattr(last, "tool_calls", None):
        return "tools"
    return "end"

graph.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})

Same underlying graph-theory idea as "which edge do I take" — just evaluated live against what the LLM actually said, not a number baked in ahead of time.

In graph theory, a source is a node nothing points into (where a path can begin) and a sink is a node nothing points out of (where a path must end). LangGraph makes these explicit rather than implicit:

graph.set_entry_point("agent")
...
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})

`END` isn't a real node with logic in it — it's a sentinel value meaning "the traversal is over, return the final state." Every LangGraph run is, formally, a walk from a source to a sink through however many cycles it takes to get there.

A graph traversal by itself doesn't have to carry anything — you can walk a road map without remembering what you saw at the last city. LangGraph's key addition is a shared state object that flows along every edge and accumulates as nodes run:

class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], operator.add]

Every time `tools_node` runs, its output messages get appended (`operator.add`) to what's already there, and the whole accumulated list is what `agent_node` sees on the next visit — so the LLM's second pass through the loop knows everything the first pass learned.

Nothing says a system has to have only one graph. MedFlow compiles a separate small graph per role — Nurse's 2-node graph and Physician's 2-node graph have the same shape but different tools bound to the `agent` node:

ROLE_CONFIG = {
    "NURSE": (NURSE_TOOLS, NURSE_SYSTEM_PROMPT),
    "PHYSICIAN": (PHYSICIAN_TOOLS, PHYSICIAN_SYSTEM_PROMPT),
    ...
}

Choosing which graph to walk (by Keycloak role, never by chat text — see Training → RBAC in LangGraph) happens once, before any traversal begins. It's the graph-theory equivalent of picking which city map to open before you start navigating, rather than trying to use one giant map of every city at once.

The one-line mapping for each
NodesPython functions (`agent_node`, `tools_node`)
Directed edges`add_edge("tools", "agent")` — one-way, explicit
CyclesThe agent ↔ tools loop — LangGraph's whole reason to exist
Weighted / conditional edges`add_conditional_edges` + a routing function evaluated live
Source / sink`set_entry_point(...)` and `END`
Data carried along the walkThe shared `AgentState` (`messages` list)
